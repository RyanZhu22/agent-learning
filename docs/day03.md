# 第 3 天：让助手根据自己的知识库回答

今天用约 3 小时，把“模型凭已有知识聊天”推进到“先找资料，再根据资料回答”。
你会运行一个带来源引用的客服问答程序，并亲自检查它找到的原文。
第 2 天的工单查询代码保持原样；今天先把知识库这一部分单独做清楚。

| 时间 | 动手任务 | 完成标志 |
| --- | --- | --- |
| 0–45 分钟 | 理解流程，建立本地索引 | 看见文档数、片段数和 512 维向量 |
| 45–100 分钟 | 单独检索，读原文，运行评测 | 能说明候选资料为什么能或不能回答问题 |
| 100–180 分钟 | 生成带引用的回答，测试资料外问题，更新文档 | 能核对引用、观察拒答和资料更新 |

## 第一段：理解分工，再建立索引（45 分钟）

先认识今天的三个阶段：

```text
建立索引：文档 → 切成片段 → 本地模型生成向量 → 存入 Chroma
检索资料：问题 → 同一个本地模型生成向量 → 找到相近片段
生成回答：问题 + 找到的片段 → DeepSeek → 回答 + 来源编号
```

**Embedding 模型负责“帮助查找”。**
FastEmbed 在本机运行 `BAAI/bge-small-zh-v1.5`，把中文文本转成 512 个数。
这些数来自模型计算，用于比较文本含义；它不会生成客服回答。

**Chroma 负责“保存和查找向量”。**
我们同时存入片段原文、文件名和分段编号，找到向量后就能取回原文。
文档和问题必须使用同一个 embedding 模型，不能把不同模型的向量混在一起。

**DeepSeek 负责“阅读资料并组织回答”。**
它会收到当前问题和检索出的片段，不会自动读取整个知识库。
资料可能不完整，所以“找到了相似片段”还不等于“已经找到了答案”。

打开 `day03_retrieval.py`，先看 `read_chunks()`、`build_index()` 两个函数。
切分方式刻意保持简单：按文档字符串每 240 个字符取一个窗口，相邻窗口重叠 40 个字符。
每个片段前还会附上文档标题，帮助保留主题。
这里使用 Python 字符数，**240 个字符不等于 240 个 token**。
模型按 token 处理文本；本模型超过 512 tokens 的输入会截断。
40 字符重叠用于保留切口附近的信息，也会让相邻片段包含一部分相同文字。

现在建立索引：

```bash
uv run day03_rag.py --index
```

首次在新机器运行会联网下载公开中文模型，本机已经缓存；此步骤不调用 DeepSeek。
建库成功后，应看到读取的文档数、片段数和每个向量为 512 维的提示。
开发时本地实测：10 篇文档切成 21 个片段，每个向量 512 维；这不是你已经完成练习的记录。
模型保存在 `artifacts/embedding_cache/`，索引保存在 `artifacts/chroma_day03/`。
模型和索引齐备后，检索只使用本地缓存，可以离线运行。
若模型缓存缺失，先联网运行 `--index`，不要用随机数或哈希值代替向量。

`--index` 先生成全部向量，再替换本课专用集合 `day03_product_docs_v1`。
它不会清空其他集合；重建也不会把同一批片段反复追加进去。
集合的 metadata 保存资料、文件名、模型名和分块配置的指纹。
资料或这些配置变化后，检索会提示重建，避免继续使用旧内容的向量。

## 第二段：先看检索原文（55 分钟）

先不生成回答，只查本地资料：

```bash
uv run day03_rag.py --search-only "邮件通知失败怎么办？"
```

这条命令不调用 DeepSeek。仔细读输出中的原文，找到邮件失败、重试和排查步骤。
默认先找最相近的 3 个片段，再过滤低于 `0.35` 相似度的结果，因此可能少于 3 个。
这里的“3”指 3 个片段，可能来自同一个文件，不保证来自 3 篇不同文档。
开发时，这个问题的前两段来自邮件文档，第三段来自 Webhook 文档；应逐段判断是否支持当前问题。

输出中的两个编号用途不同：

- `mail_notifications.md#chunk-2`：文件名和第 2 个片段，用于回到原文定位。
- `[S1]`：本次问题的第 1 条候选资料，供后面的回答引用。

换一个问题，`S1` 可能对应另一个片段，它不是跨问题固定的文档编号。
修改文档或切块设置后，同一 `chunk-2` 中的文字也可能变化。

集合使用 cosine 距离，代码通过 `1 - distance` 显示余弦相似度。
分数越高，通常说明模型认为文本含义越接近。
**分数不是概率，也不是回答正确率。** `0.8` 不表示答案有 80% 的概率正确。
默认阈值 `0.35` 是本课实验起点，需要用实际问题观察效果。

对照运行一次：

```bash
uv run day03_rag.py --search-only "邮件通知失败怎么办？" --top-k 1
```

比较两次输出：只有 1 个片段时，是否缺少重试次数或完整排查步骤？
不要为了得到更多结果就断定结果更好，先检查每段是否提供了需要的事实。

再运行固定检索案例：

```bash
uv run day03_rag.py --eval
```

共 10 题，全程只做本地检索，不调用 DeepSeek。
其中 8 道资料内问题参与评分，要求命中预期文件，且命中片段包含预期事实。
另外 2 道资料外问题只列出候选资料，不计入这个分数。
结果保存在 `artifacts/day03_retrieval_report.json`。
开发时本地验收为资料内 8/8；资料外两题仍有相似候选，不能据此声称模型已正确拒答。
这个报告衡量“有没有找到预期依据”，不衡量生成答案、引用是否正确或是否会拒答。
退款问题检索到相似片段也不算找到退款政策；拒答需要下一段单独验证。

## 第三段：生成回答，核对引用，更新资料（80 分钟）

运行完整问答：

```bash
uv run day03_rag.py "邮件通知失败怎么办？"
```

程序会先打印检索原文，再把问题和这些片段发给 DeepSeek，调用一次真实 API。
如果本地检索没有候选片段，程序直接提示资料不足，不发起模型请求。
本课使用固定的 RAG workflow：程序规定先检索、再生成。
**它尚未接入第 2 天的 Agent**，模型不会自主选择查文档还是调用工单工具。

打开 `day03_rag.py`，阅读 `SYSTEM_PROMPT` 和 `answer_with_docs()`。
模型被要求只根据提供的资料回答，不用常识补充产品规则，也不能声称执行过操作。
输出先经过字段校验，再检查来源编号是否合法，以及“能回答”时是否提供来源。
但这只检查引用 ID，不会自动证明“答案的每句话都得到原文支持”。
因此要亲自完成一次核对：读回答 → 看依据 `[S1]` → 找对应片段 → 对照具体事实。
当前已经验证本地检索和模拟 API 流程，真实生成质量需要你运行后再验收。

接着测试两个知识库没有答案的问题：

```bash
uv run day03_rag.py "申请退款后，款项需要几个工作日到账？"
uv run day03_rag.py "如何配置钉钉扫码登录云工单工作台？"
```

若有候选片段，每条命令会调用一次 DeepSeek；预期回答应说明资料没有相关政策或步骤。
观察它有没有编造到账天数、配置入口，或者把相似片段错误引用成依据。
若没有候选片段，则由程序直接提示资料不足；这两种路径都要能解释清楚。

最后做一次资料更新练习，文件由你亲手修改：

1. 先检索并回答“邮件通知首次发送失败后，最多重试多少次？”，记录当前依据和答案。
2. 在 `knowledge/mail_notifications.md` 中，把“最多重试3次”改成“最多重试4次”。
3. 再运行 `--search-only`，预期会提示资料变化、需要重建索引。
4. 运行 `uv run day03_rag.py --index`，随后对同一个问题重新检索、生成回答。
5. 核对新片段和新答案是否都使用“4次”，且片段总数没有因重复入库而持续增长。

不要直接往旧集合追加一份新文档；本课通过替换专用集合避免旧片段和新片段混用。
完成后可保留你修改的演示规则，并在笔记中记录这次更新。

## 今天的验收与延伸阅读

- 能画出索引、检索、生成三个阶段，说明哪一步会调用真实 DeepSeek API。
- 能对照原文核实一个带引用的答案，而不只看模型写得是否流畅。
- 能解释资料外问题的拒答，以及检索评分和回答正确率的区别。
- 能通过修改文档、重建索引观察新事实，并说明为何不能保留重复向量。
