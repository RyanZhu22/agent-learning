# 第 4 天第一部分：让同一个 Agent 选择查工单还是查文档

今天先连接第 2、3 天已经完成的能力。等工具选择验证通过，再学习报修草稿；实际建单、确认与防重复在第 5 天完成。

## 今天有什么变化

第 3 天是固定流程：Python 先检索，再把片段交给 DeepSeek。
现在由模型判断是否需要工具，以及需要哪一个工具：

| 问题 | 预期工具 |
| --- | --- |
| 查询工单 T1004 的状态 | get_ticket |
| 邮件通知首次发送失败后最多重试几次 | search_docs |
| 查询 T1004，并告诉我邮件通知失败的排查方法 | 两个工具 |
| 帮我查一下工单状态 | 先追问编号 |
| 你好 | 可直接回复 |

这些是验收预期，不是 Python 写死的关键词路由。程序发送同一份工具清单，由模型选择。是否选择正确，需要看实际输出。

“4次”来自你更新的资料，不是程序写死的答案。

## 对照代码看四个连接点

打开 day04_agent.py：

1. `TOOLS`：给模型看的两份工具说明，包含名称、用途和参数 Schema。
2. `TOOL_MODELS`：给 Python 用的参数校验模型，每种工具有自己的入参要求。
3. `TOOL_FUNCTIONS`：把名称对应到真正的 Python 函数。
4. `run_agent()`：反复请求模型，执行工具，回传结果，直到生成最终回复或达到上限。

与第 2 天相比，变化不是多写一个关键词判断，而是把工具清单从一项扩展成两项。

```python
TOOL_FUNCTIONS = {
    "get_ticket": get_ticket,
    "search_docs": search_docs,
}

TOOL_MODELS = {
    "get_ticket": TicketQuery,
    "search_docs": DocsQuery,
}
```

模型可能请求：

```text
get_ticket，参数 {"ticket_id":"T1004"}
```

也可能请求：

```text
search_docs，参数 {"question":"邮件通知失败的重试规则"}
```

`execute_tool()` 根据名称选择参数模型：

```python
query = TOOL_MODELS[name].model_validate_json(arguments)
data = TOOL_FUNCTIONS[name](**query.model_dump())
```

第一种工具验证工单号格式，第二种工具验证非空问题字符串。
模型给 get_ticket 传 question 字段，或给 search_docs 传 ticket_id 字段，都会被拒绝。
工单查询返回字典；检索返回片段列表。两者都包装为 `{"ok": true, "data": ...}`，失败也返回结构化错误。

## 文档检索工具只找资料，不再内部调用一次 DeepSeek

这里直接调用 day03_retrieval.py 的 search_docs，而不是运行 day03_rag.py 的完整问答程序。
search_docs 只使用本地中文向量模型和 Chroma，返回原文片段。
当前 Agent 读取这些片段后，继续同一个模型循环并生成回答。

```text
用户问题
→ DeepSeek 请求 search_docs
→ Python 本地检索，返回原文
→ DeepSeek 根据原文组织回答
```

程序没有先运行第 1 天的分类器，也没有另建一个专门负责知识库的 Agent。

## 来源如何保存

每次运行有两个字典：sources 保存编号与片段，source_labels 保存片段与编号的对应关系。
检索结果进入模型上下文前，程序给每个片段加入 source_id，例如 S1。
同一片段被重复检索时保留原编号；新片段使用新编号，避免第二次检索的 S1 覆盖第一次。

最终回复沿用第 3 天的三个字段：

```json
{"can_answer":true,"answer":"邮件通知最多重试4次。","source_ids":["S1"]}
```

这里的措辞和来源编号仅是示意，不能当作真实运行记录。
程序通过 Pydantic 校验字段，再检查来源编号确实来自本次工具结果。
仅查工单时 source_ids 应为空，因为依据是工单工具的数据，不是 Markdown 片段。
如果已有文档候选、模型声明能回答却不给出处，程序会停止并提示。
这不能自动证明每句话都被资料支持，仍要人工对照原文。

## 再测试组合问题与边界

```bash
uv run day04_agent.py "查询工单 T1004 的状态，并告诉我邮件通知失败如何排查"
uv run day04_agent.py "帮我查一下工单状态"
uv run day04_agent.py "申请退款后，款项需要几个工作日到账？"
```

组合问题可能在同一轮请求两个工具，也可能分两轮先后调用。两种顺序都可以，重点是数据来源正确。
缺少编号应追问；退款问题应查资料后说明现有文档不足，不编造到账天数。
单次命令只处理一个用户问题，不保留跨命令历史；补充编号时重新输入完整问题。
默认最多 4 轮模型请求、最多处理 6 次工具请求，模型输出截断时不执行本轮工具。
资料变更或索引缺失时，search_docs 返回错误，先按提示重新运行第 3 天的 --index。

用表格记录：输入问题｜实际工具名｜参数｜工具结果｜最终事实｜来源是否支持结论。

- 缺编号时追问，资料外问题说明缺口。
- 能指出代码中工具说明、参数模型和函数登记表的区别。

## 第二部分：收集信息并整理报修草稿

现在同一个 day04_agent.py 增加了 prepare_ticket_draft 工具，字段模型与纯函数放在 day04_draft.py，不需要新依赖。
它返回结构化字段和 created=false，不写文件、不分配工单编号，也不修改 TICKETS。

先试信息不足的情况：

```bash
uv run day04_agent.py "我要报修：邮件通知失败，请帮我整理工单草稿。"
```

预期追问复现步骤、期望结果、实际结果和发生时间，不得编造这些内容后调用草稿工具。
当前命令之间不共享历史。下一次必须重新输入完整描述，不能只输入“今天上午”。

再试完整信息（以下是虚构的练习输入）：

```bash
uv run day04_agent.py "请整理报修草稿。问题描述：邮件通知功能异常。复现步骤：进入通知设置，点击发送测试邮件。期望结果：测试邮箱收到邮件。实际结果：页面提示连接超时，邮箱未收到邮件。发生时间：2026年10月23日10:00，UTC+8。"
```

预期调用 prepare_ticket_draft，展示六项字段：标题、问题描述、复现步骤、期望结果、实际结果、发生时间。
标题由模型概括，其他信息必须忠实于用户描述。时间先保留用户原话，不做时区换算。
最终明确“仅为草稿，尚未创建工单”；单纯整理草稿不必查文档，也没有文档来源编号。

阅读顺序：

1. day04_draft.py 的 TicketDraft：定义字段和约束。
2. day04_agent.py 的三个登记位置：TOOLS、TOOL_MODELS、TOOL_FUNCTIONS。
3. execute_tool：JSON 参数先通过 Pydantic，再执行 prepare_ticket_draft。
4. prepare_ticket_draft：只返回字典，由原来的循环交给模型展示。

Pydantic 能检查字段缺失、空白字符串、类型和长度，不能证明内容真的由用户提供。
“不得编造字段”目前靠提示词约束，并需人工对照用户输入验收。不要把格式校验通过当成事实校验通过。
本节没有多轮会话收集或草稿持久化；第 5 天继续学习确认后建单、持久化与防重复。

参考：[DeepSeek 官方工具调用](https://api-docs.deepseek.com/guides/tool_calls/)。本课使用官方非思考模式，并由本地 Pydantic 校验参数。
