# 第 5 天：核对草稿，确认后创建本地工单

第 4 天已经能把报修描述整理成六个字段。今天让草稿在程序退出后仍然存在，并学习怎样把一次明确确认变成一次可靠的写入。

本课约 3 小时。先运行离线演示，再读关键代码，最后自己操作取消、重复确认和失败场景。运行成功只是起点；你还要能解释每一步为什么发生、数据库里留下了什么。

今天新增的文件各有职责：

| 文件 | 职责 |
| --- | --- |
| `day05_agent.py` | 命令入口、整理草稿、展示草稿与人工确认 |
| `day05_store.py` | SQLite 保存草稿、创建工单、事务与防重复 |
| `data/day05_draft.json` | 六字段离线练习样例 |
| `tests/` 中的第 5 天测试 | 自动检查写入、失败回滚和重复确认等行为 |

第 1–4 天文件保留。查知识库继续使用 `day04_agent.py`；今天没有网页，也没有连接企业工单系统。数据库中的草稿和工单都是本机学习数据。

## 0–20 分钟：先观察完整演示

在 PowerShell 中进入项目目录，运行：

```powershell
Set-Location D:\codex\agent-learning
python day05_agent.py demo
```

这个命令完全离线，不需要 API Key、向量模型或知识库索引。它用临时数据库演示以下过程：

1. 保存一份完整草稿，得到草稿编号。
2. 直接调用存储层但不传确认标记，观察创建被拒绝。
3. 模拟用户取消，观察没有工单被创建。
4. 模拟明确确认，创建一张本地工单。
5. 对同一份草稿再次确认，拿到原来的工单编号。
6. 重新打开数据库，再查询已经创建的工单。

记录输出中出现的草稿号、首次工单号和重复确认返回的工单号。不要只看最后一行“成功”，要逐项核对：取消时有没有写入？重复时有没有多建一张？重新打开后还能不能查到？

演示里的确认是程序自动模拟的。后面的 `confirm` 命令才会要求你在终端手动输入确认短语。
演示使用临时库，不会把示例写进默认的学习数据库。

项目要求的完整环境仍是 Python 3.12，可用 `uv sync` 安装依赖，再运行 `uv run day05_agent.py demo`。
本课离线路径刻意不提前加载模型 SDK，也可用本机现有 Python 3.11 运行；这没有修改 `pyproject.toml` 的版本要求。

## 20–50 分钟：亲手保存、核对与确认

先用 JSON 样例练习。完整项目环境的命令如下；若当前只使用现有 Python，离线命令可以把开头的 `uv run` 换成 `python`。

```powershell
uv run day05_agent.py prepare --from-json data/day05_draft.json
```

这一步校验六个字段，保存草稿并显示编号。**保存草稿不等于创建工单。**

把下面命令的 `Dxxx` 换成刚才的实际草稿编号：

```powershell
uv run day05_agent.py show Dxxx
uv run day05_agent.py confirm Dxxx
```

尚未提交的草稿运行 `confirm` 时，会重新读取并展示这份已经保存的完整草稿。先核对标题、问题描述、复现步骤、期望结果、实际结果、发生时间，再输入：

```text
确认创建 Dxxx
```

这里也必须使用实际编号。只有精确匹配这句话才创建工单；输入“好的”“确认”，直接回车，或使用别的编号，都取消这次操作。
先试一次取消，再运行同一条 `confirm` 命令并输入正确短语。

得到实际工单编号后查询：

```powershell
uv run day05_agent.py get Nxxx
```

关闭终端、重新打开并回到项目目录，再查询一次。结果来自 SQLite 中已保存的数据。`get T1004` 仍查询前几天的本地模拟数据，`N` 开头的编号用于今天创建的持久化工单。

默认数据库位于 `artifacts/day05_tickets.sqlite3`。想为练习使用独立数据库时，把全局参数写在子命令前：

```powershell
uv run day05_agent.py --db artifacts/day05_practice.sqlite3 prepare --from-json data/day05_draft.json
uv run day05_agent.py --db artifacts/day05_practice.sqlite3 show Dxxx
uv run day05_agent.py --db artifacts/day05_practice.sqlite3 confirm Dxxx
uv run day05_agent.py --db artifacts/day05_practice.sqlite3 get Nxxx
```

这些命令必须指向同一个数据库。更换路径就是使用另一份数据，不会自动找到旧库中的编号。

## 50–80 分钟：让模型整理草稿，人工核对事实

准备好 Python 3.12、`uv sync` 和本地 `.env` 后，再运行真实模型路径。沿用 `DEEPSEEK_API_KEY`，不要把密钥贴到聊天或写进练习记录。

先试信息不足的输入：

```powershell
uv run day05_agent.py prepare "我要报修：邮件通知失败。"
```

预期说明还缺哪些信息并追问，不保存不完整草稿，也不创建工单。当前命令之间没有自然语言会话历史，补充信息时重新提供完整描述。

再试完整的虚构描述：

```powershell
uv run day05_agent.py prepare "请整理报修草稿。问题描述：邮件通知功能异常。复现步骤：进入通知设置，点击发送测试邮件。期望结果：测试邮箱收到邮件。实际结果：页面提示连接超时，邮箱未收到邮件。发生时间：2026年10月24日10:00，UTC+8。"
```

模型负责整理六个字段，Python 校验后只保存并展示草稿。它不能通过工具直接创建工单。
标题可以概括，但其余信息要与用户输入一致。特别检查复现步骤、实际错误和发生时间；格式合法不代表事实正确。
若草稿有误，先修改原始描述或 JSON，再准备一份新草稿。今天没有草稿编辑命令，不要确认错误内容。

读代码时找出这个边界：模型整理阶段没有创建工具；本地 `confirm` 命令读取已经保存的草稿，收到终端确认后，才调用存储层执行创建。

## 80–115 分钟：读懂保存、确认与事务

按下面顺序阅读代码，每读一处就回到命令输出核对一次。

1. `day04_draft.py` 中的 `TicketDraft`：沿用六字段约束，缺字段或空白字符串不能成为完整草稿。
2. `day05_agent.py` 中的 `DraftProposal`、`extract_proposal()` 与 `main()` 的 `prepare` 分支：模型输出或 JSON 输入先经过校验，再保存草稿。模型请求失败、内容不完整或格式错误时，不应留下可确认的完整草稿。
3. `day05_agent.py` 中的 `confirm_from_console()`：读取并展示保存的内容，检查终端短语，再调用存储层。找到实际执行写入的位置。
4. `day05_store.py` 的 `TicketStore`：依次看 `save_draft()`、`get_draft()`、`confirm_draft()` 和 `get_ticket()`，找到草稿表、工单表、草稿与工单之间的关联，以及创建过程中的事务。

数据流可以写成：

```text
用户描述或 JSON
→ 六字段校验
→ 保存草稿 Dxxx
→ 展示已保存的完整草稿
→ 用户输入“确认创建 Dxxx”
→ 一个事务内创建工单并记录与草稿的关系
→ 返回工单 Nxxx
```

SQLite 事务把相关写入放在同一个提交边界内。创建过程中出现异常时，相关变更一起回滚，不能只留下部分成功的状态。
草稿可以仍然存在，因为保存草稿是前一个已完成的动作；失败的是这一次“从草稿创建工单”的操作。

事务与确认解决不同问题：确认说明用户允许对这份草稿执行创建；事务确保程序执行过程中失败时，数据库不会只完成一半。

今天的确认适用于单用户、本机命令行练习。终端中的精确短语不是身份认证，也没有提供多用户权限管理。

## 115–140 分钟：理解按草稿编号防重复

再次确认刚才已经创建过的草稿：

```powershell
uv run day05_agent.py confirm Dxxx
```

已提交的草稿应直接返回同一张工单，不再要求输入确认短语，也不会生成新编号。
这叫幂等：同一份草稿的创建操作重复执行，结果仍指向同一张工单。
数据库用草稿编号关联工单，并通过唯一约束阻止同一草稿对应多张工单。

再用相同 JSON 运行一次 `prepare`。你会得到新的草稿编号；确认新草稿可以得到新的工单。
这是因为本课把每次准备草稿视为一次新的意图，按 `draft_id` 防重复，没有按内容去重。

思考这两个场景：

| 操作 | 预期 |
| --- | --- |
| 同一个 `Dxxx` 重复确认 | 返回同一个 `Nxxx` |
| 同样内容重新 `prepare`，确认新草稿 | 可以创建另一张工单 |

因此，用户不确定刚才是否成功时，应先查旧草稿或工单、重试原草稿，而不是重新准备相同内容。
读存储层，找出“查已有工单”和数据库唯一约束各自发挥作用的位置。只靠先查询一次，并不能替代数据库约束。

## 140–165 分钟：检查失败场景

运行离线自动测试：

```powershell
python -m unittest discover -s tests -v
```

在完整项目环境中也可以运行：

```powershell
uv run python -m unittest discover -s tests -v
```

测试使用临时数据库，不需要调用 DeepSeek。阅读 `tests/test_day05_store.py` 中的 `test_failed_update_rolls_back_insert_and_allows_retry()`：它用 SQLite trigger 模拟更新草稿时出错，再核对工单插入也被回滚、原草稿仍然待确认，移除故障后可以重试。
失败回滚测试应实际触发异常，再检查数据库结果；只检查返回了一条错误文本不够。

再手工检查三个输入边界：

- 对已保存的草稿输入错误确认短语，核对没有新工单。
- 查询一个不存在的草稿号或工单号，观察明确的失败提示。
- 复制 JSON 样例到自己的练习文件，删去一个必填字段，再运行 `prepare --from-json`，核对校验失败且没有保存新草稿。

不要为制造失败删除自己的默认数据库。临时库和单独练习库足以完成本课。

## 165–180 分钟：小练习与验收

选一个真实但不含敏感信息的问题，或再编一个虚构故障：先写完整描述，整理成草稿，逐项核对后取消一次，再确认创建。保存你的命令、实际编号和观察结果。

在记录中回答三个问题：

1. 为什么 `prepare` 成功后还没有工单？
2. 用户重复确认同一个草稿，与重新准备一份相同草稿，结果为什么不同？
3. 创建过程中出错时，草稿和工单应该分别处于什么状态？代码中哪里保证这一点？

| 验收项 | 你需要提供的证据 |
| --- | --- |
| 六字段完整且忠实于输入 | 原始描述与草稿逐项核对记录 |
| 取消不会建单 | 错误短语或取消后，没有创建结果 |
| 确认后本地建单 | 实际草稿号、工单号和查询结果 |
| 数据在进程退出后保留 | 新进程仍能查询相同工单 |
| 同一草稿重复确认不重复建单 | 两次返回相同工单号 |
| 能解释失败回滚 | 指出事务代码，并解释相关测试 |
| 能解释模型与写入的边界 | 指出模型整理路径与终端确认路径 |

自动测试通过表示这些程序行为通过了已有检查。完成本课还需要你亲手操作，并能解释确认、持久化、事务和幂等各自解决的问题。
