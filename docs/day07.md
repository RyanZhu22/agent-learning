# 第 7 天：固定评测、失败分析与部署说明

前六天证明了这个助手“能跑通”。今天回答三个更难的问题：怎么知道它没有变坏？失败时先看哪里？离开这台电脑还缺什么？

**能演示不等于可靠。** 一次成功的对话可能只是运气好；只有可重复的固定案例、说清口径的指标，和能定位到层的失败分析，才让“改好了”这句话有依据。

本课约 3 小时。先跑离线评测，再读评分代码，然后接真实模型、故意制造失败，最后过一遍上线前的差距清单。

| 文件                            | 职责                         |
| ----------------------------- | -------------------------- |
| `day07_eval.py`               | 评测入口：加载案例、分层执行、评分、失败分析、写报告 |
| `data/day07_cases.jsonl`      | 20 条固定案例，覆盖五个层             |
| `tests/test_day07_eval.py`    | 离线验证加载规则、评分口径与确认边界         |
| `artifacts/day07_report.json` | 逐条结果与耗时（生成物，不入库）           |
| `artifacts/day07_summary.md`  | 可直接贴进周报的摘要（生成物，不入库）        |

第 1–6 天文件全部保留。今天不改业务逻辑，只增加观测能力；这也是为什么新增代码只有评测，没有新的接口或页面。

## 0–20 分钟：先跑一次离线评测

```sh
uv run day07_eval.py
```

预期输出会先提示“跳过 11 条真实模型案例”，然后执行 9 条，最后给出总通过数和两个文件路径。

```text
离线模式：跳过 11 条真实模型案例，加 --live 运行。
共 9 条案例；模式：离线。
D7-R01 检索：通过
...
D7-K03 确认边界：通过

总通过：9/9
  检索：6/6（100%）
  确认边界：3/3（100%）
```

离线部分只做两件事：

1. **检索**：用第 3 天建好的本地索引召回文档，检查正确文档是否进入前 3 条、片段里是否真有答案。
2. **确认边界**：用临时数据库和模拟模型检查三条硬规则——未确认不建单、错短语被拒、重复确认幂等。

它不调用 DeepSeek、不需要密钥、不写你的学习数据库。所以可以每天跑、每次改代码后跑，成本为零。

如果提示“尚未建立知识库”，先建索引再重试：

```sh
uv run day03_rag.py --index
```

先看 `artifacts/day07_summary.md`。它是给人读的；`day07_report.json` 是给程序读的，里面有每条案例的耗时和失败原因。

## 20–50 分钟：五层评测集与指标口径

固定案例一共 20 条，按层分组。分层不是为了好看，而是因为**失败必须能定位到某一层**。

| 层         | 条数 | 检查什么              | 判定方式                        | 需要 API |
| --------- | -- | ----------------- | --------------------------- | ------ |
| 检索        | 6  | 正确文档是否被召回，片段是否含答案 | 正确文档进入前 3 条 **且** 片段包含预期事实  | 否      |
| 确认边界      | 3  | 写入是否可能被绕过         | 三条硬规则全部成立                   | 否      |
| 分类        | 4  | 意图标签              | `intent` 与标注一致              | 是      |
| 草稿整理      | 3  | 是否追问、缺失字段是否说全     | 状态一致 **且** 缺失字段覆盖标注         | 是      |
| 端到端 Agent | 4  | 是否调用工具、是否诚实拒答     | `can_answer`、答案关键词、来源数量同时满足 | 是      |

几个容易含糊的口径，这里一次说清：

- **检索通过 ≠ 回答正确。** 命中片段只说明“资料找到了”，模型是否忠实引用仍要人工核对。这也是第 3 天就强调过的：相似度不是正确率。
- **草稿缺失字段允许“多报”，不允许“漏报”。** 模型多列一个缺失字段会让用户多回答一句；漏列会让草稿带着编造内容进入确认环节，风险方向完全不同。
- **端到端用关键词而不是语义相似度。** 关键词会漏判同义表述，但它可复现、可解释；用模型给自己打分，只会让评测变成另一个不确定源。
- **通过率不是分数榜。** 100% 只说明这 20 条通过了。案例没覆盖的输入，仍然可能错。

按下面的顺序读 `day07_eval.py`，不必一次看懂全部：

1. `load_cases()`：为什么缺字段在加载时就报错，而不是运行到一半才发现。
2. `grade_retrieval / grade_classify / grade_draft / grade_agent`：四个纯函数，不碰数据库也不调模型，所以能被单元测试直接覆盖。
3. `CONTRACT_CHECKS`：三条确认边界的实现，全部使用临时目录。
4. `evaluate()`：单条案例失败只记录，不中断整轮。
5. `analyze_failures()`：把失败归到“层 + 原因”，并附一句下一步建议。

## 50–80 分钟：接真实模型

```sh
uv run day07_eval.py --live
```

这一次会跑满 20 条。分类、草稿、端到端三层会调用真实 DeepSeek API；端到端每条通常需要两轮模型请求，所以实际请求数多于案例数。终端只显示通过与否，工具选择过程被收进缓冲区，避免刷屏。

预期全部通过。但请接受一个事实：**同一批案例在不同时间跑，结果可能不同。** 模型有随机性，服务也可能波动。遇到偶发失败，正确做法是记录当时的时间、模型和错误类型，重复跑几次确认是否稳定；**不要为了让指标好看去改标注**。改标注是让评测迁就模型，那这张网就失效了。

跑完后对比两个模式：

| 观察项    | 离线    | `--live`  |
| ------ | ----- | --------- |
| 案例数    | 9     | 20        |
| 是否消耗额度 | 否     | 是         |
| 结果是否稳定 | 是     | 大体稳定，可能波动 |
| 适合频率   | 每次改代码 | 每天一次或发布前  |

## 80–110 分钟：故意制造失败，练习分析

全绿的报告学不到东西。主动弄坏一层，看报告是否指得准。

把检索阈值调高，让正确片段被过滤掉：

```sh
uv run day07_eval.py --min-similarity 0.8
```

预期 6 条检索全部失败，原因统一是 `source_miss`，失败分析给出“检查切分粒度、top_k、相似度阈值或问题表述”。命令以退出码 `1` 结束——这一点很重要，它意味着这个脚本可以直接放进 CI，失败会真的让流水线变红。

再换一种坏法：把 `top_k` 压到 1。

```sh
uv run day07_eval.py --top-k 1
```

观察是否仍然全绿。如果通过，说明正确片段本来就排第一；如果失败，说明排序不稳，问题不在阈值而在检索质量。

第三种坏法是改数据而不是改参数：打开 `data/day07_cases.jsonl`，把 `D7-R01` 的 `expected_fact` 从 `587` 改成 `465`，再跑一次。这次会得到 `fact_miss`——**文档找对了，但片段里没有这个事实**。改完记得改回来。

三种原因的区别，是今天最该记住的东西：

| 原因                 | 含义             | 通常的修法               |
| ------------------ | -------------- | ------------------- |
| `source_miss`      | 正确文档根本没进候选     | 调切分、top_k、阈值，或改问题表述 |
| `fact_miss`        | 文档进来了，但片段不含答案  | 答案跨片段或切得太碎，调整切分策略   |
| `answer_text_miss` | 资料对了，回答里却没有该事实 | 模型没调用工具，或引用了错误片段    |

失败分析里的每条建议都对应一个可执行动作。看到“先停下修服务端校验”这类提示时，意思是**不要合并、不要发布**，而不是“稍后再看”。

## 110–150 分钟：部署说明

这一节讲“换一台机器还能跑”，以及“真要给别人用还缺什么”。两者不是一回事。

### 本机长期运行

前台运行最简单，关掉终端服务就停：

```sh
uv run day06_api.py
```

需要它在关闭终端后继续跑，可以用 `tmux` 或 `nohup`：

```sh
nohup uv run day06_api.py --port 8000 > artifacts/server.out 2>&1 &
```

换端口、换数据库、换日志路径都通过参数控制：

```sh
uv run day06_api.py --port 8001 --db artifacts/day07_practice.sqlite3 --log artifacts/day07_api.log
```

日志按 1 MB 轮转、保留 2 份，所以不会无限增长。数据在 SQLite 里，停服务不会丢。

### 换一台机器复现

1. 安装 `uv`，确认 Python 3.12（`.python-version` 已固定）。
2. `uv sync` 安装依赖。
3. 复制 `.env.example` 为 `.env`，填入 `DEEPSEEK_API_KEY`。
4. `uv run day03_rag.py --index` 重建索引（首次会下载向量模型，需要联网）。
5. `uv run day07_eval.py` 自检：9 条离线案例应全绿。
6. `uv run day06_api.py` 启动服务。

第 5 步是新增的。以前“能不能跑”靠人点一遍；现在有了一条命令能回答。

### 上线前必须补的差距

下面这张表是今天最重要的产出。它明确告诉你：**这个项目不是生产系统**，差距不是“再优化一下”，而是缺整块能力。

| 项目 | 现在                             | 真要给别人用              |
| -- | ------------------------------ | ------------------- |
| 身份 | 无登录                            | 账号体系、会话、找回密码        |
| 权限 | 谁都能确认任意草稿                      | 只有报修人和受理人可操作，且要审计   |
| 传输 | 本机 HTTP                        | HTTPS + 反向代理        |
| 并发 | SQLite 单写，`BEGIN IMMEDIATE` 串行 | 连接池 + 服务型数据库，或明确排队  |
| 密钥 | `.env` 本地文件                    | 密钥管理服务，绝不入库、不进日志    |
| 限流 | 无                              | 按用户/IP 限流，模型调用设预算上限 |
| 数据 | 本机文件                           | 备份、保留期、脱敏与删除流程      |
| 日志 | 本地文件                           | 集中采集、告警、审计留存        |
| 迁移 | `CREATE TABLE IF NOT EXISTS`   | 版本化迁移脚本             |
| 评测 | 20 条固定案例                       | 持续扩充，并抽样线上真实请求      |

确认短语 `确认创建 Dxxx` 只是“表达这次确认”，**没有身份含义**。任何拿到草稿编号的人都能提交同样的短语。上线前必须用登录身份替代它。

如果只是想让局域网内同事试用，最小做法是加一层反向代理并绑定内网地址。下面仅是示意，本项目未验证：

```nginx
server {
    listen 8443 ssl;
    server_name tickets.example.internal;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header X-Request-ID $request_id;
    }
}
```

即便如此，也请先补上登录，再谈“试用”。

## 150–180 分钟：10 分钟演示脚本与验收

演示不是把功能点一遍，而是讲清一条因果链。按这个顺序走，每一步都有话说：

| 顺序 | 命令或操作                                                   | 要讲的话           | 观察什么                    |
| -- | ------------------------------------------------------- | -------------- | ----------------------- |
| 1  | `uv run day07_eval.py`                                  | 这是回归网，零成本、可每天跑 | 9/9，两个产物路径              |
| 2  | `uv run day07_eval.py --min-similarity 0.8`             | 故意弄坏，看它能不能指到层  | 6 条 `source_miss`，退出码 1 |
| 3  | `uv run day06_api.py`，页面走一遍                             | 保存不等于建单，确认才建单  | 取消后草稿仍在；重复确认返回原工单       |
| 4  | `uv run day04_agent.py "查询工单 T1004 的状态，并告诉我邮件通知失败如何排查"` | 一个循环里选多个工具     | 两次工具请求，回答带来源            |
| 5  | 打开 `artifacts/day07_summary.md`                         | 指标口径比数字重要      | 分层表格与失败分析               |

演示时不要念代码。用“用户做了什么 → 系统发生了什么 → 留下什么证据”三段式讲，比逐行解释有效得多。

验收标准是能用自己的话回答四个问题：

| 问题                               | 期望的回答要点                 |
| -------------------------------- | ----------------------- |
| 检索通过为什么不是回答正确？                   | 命中片段只证明资料找到了，忠实引用要另验    |
| 为什么确认边界要单独评测？                    | 它决定会不会误建单，属于不可回退的写入     |
| `source_miss` 和 `fact_miss` 差在哪？ | 前者没召回，后者召回了但片段没答案       |
| 这个项目上线还缺什么？                      | 身份、权限、HTTPS、并发、密钥、限流、备份 |

如果四个问题都能答，你已经具备“把 Demo 讲成系统”的能力；这比多写一个接口更难，也更有用。
